# 爬虫 Skill 方案调整：迭代式研究、主题约束与本地知识归档

这次调整后，我建议把这个 Skill 从原先的「分阶段爬虫」进一步升级为 **基于 ReAct 思路的迭代式研究 Skill**。

它不再只是执行一次搜索、抓取并生成报告，而是每完成一轮研究，就从已有资料中提炼高价值信息，判断当前研究还有哪些空白，再决定下一轮应该搜索什么。

同时，所有研究结果按主题独立归档，并提供本地 HTML 查看界面。

整个系统的核心是：

**执行一轮研究 → 提炼高权重摘要 → 评估研究缺口 → 生成下一步行动 → 执行新一轮研究 → 更新知识库 → 判断是否继续。**

这里需要区分两种能力：

- **ReAct 式执行**：根据当前观察结果决定下一步行动，再根据行动结果调整计划。
- **迭代式研究**：通过多轮信息采集、分析与反思，逐步提高研究的广度、深度和完整性。

两者结合后，才能让 Skill 不仅会抓取信息，还能持续判断「下一步最值得查什么」。

## 一、重新设计整体架构

建议将系统划分为五个部分：

1. **Research Planner：研究规划器**，负责确定主题、目标、范围和约束。
2. **Research Loop：迭代研究引擎**，负责每轮行动、观察、总结和下一步决策。
3. **Compliance & Collection：合规采集层**，负责来源检查、信息采集和正文提取。
4. **Knowledge Archive：本地知识库**，负责分类、归档、去重和检索。
5. **HTML Viewer：本地查看器**，负责以简单网页的形式查看研究结果。

推荐架构如下：

```text
用户提出研究目标
        │
        ▼
┌─────────────────────────┐
│  Research Planner       │
│                         │
│  研究主题 / 目标 / 范围 │
│  关键词 / 预算 / 约束   │
└────────────┬────────────┘
             ▼
┌─────────────────────────┐
│     Research Loop       │
│                         │
│  ┌───────────────────┐  │
│  │ 1. Action         │  │
│  │ 检索、采集、补充   │  │
│  └─────────┬─────────┘  │
│            ▼            │
│  ┌───────────────────┐  │
│  │ 2. Observation    │  │
│  │ 评估新信息与证据   │  │
│  └─────────┬─────────┘  │
│            ▼            │
│  ┌───────────────────┐  │
│  │ 3. Reflection     │  │
│  │ 提炼高权重摘要     │  │
│  └─────────┬─────────┘  │
│            ▼            │
│  ┌───────────────────┐  │
│  │ 4. Next Action    │  │
│  │ 继续、深入、扩展   │  │
│  │ 或停止             │  │
│  └─────────┬─────────┘  │
│            │            │
│            └──循环──────┘
└────────────┬────────────┘
             ▼
┌─────────────────────────┐
│ Compliance & Collection │
│                         │
│ 来源检查 / 采集 / 清洗  │
│ 结构化 / 去重 / 评分    │
└────────────┬────────────┘
             ▼
┌─────────────────────────┐
│     Knowledge Archive   │
│                         │
│ 分类目录 / JSONL / CSV  │
│ 原文记录 / 摘要 / 索引  │
└────────────┬────────────┘
             ▼
┌─────────────────────────┐
│      HTML Viewer        │
│                         │
│ 研究总览 / 文档列表     │
│ 文档详情 / 迭代历史     │
└─────────────────────────┘
```

需要强调：图中的采集层是研究引擎调用的受控能力，而不是可以绕过研究计划、独立无限爬取的后台进程。

每轮采集都必须经过同一套合规闸门，并且只能在当前研究任务的允许范围内执行。

## 二、核心机制：让每轮研究都产生下一轮行动

这是本次调整最重要的部分。

我建议不要把整个流程简单设计成一个无限循环的 Agent，而是设计成一个**有状态、有预算、有停止条件的研究循环**。

### 2.1 一轮研究的完整过程

每轮研究固定执行六个步骤：

| 步骤 | 名称 | 具体任务 | 输出 |
|---|---|---|---|
| 1 | Action | 根据当前研究计划执行检索和采集 | 新增文档 |
| 2 | Observation | 评估新增文档的质量、相关性和价值 | 观察记录 |
| 3 | Evidence Extraction | 提取重要事实、技术方案和证据 | 证据集合 |
| 4 | Reflection | 更新高权重摘要，判断已有认识是否变化 | 本轮研究摘要 |
| 5 | Next Action | 判断应深入、扩展、验证还是停止 | 下一轮行动计划 |
| 6 | Persist | 保存全部结果和状态 | 可恢复的研究状态 |

其中，`Reflection` 和 `Next Action` 是最重要的两个步骤。

前者回答：

> 这一轮研究让我们知道了什么？哪些内容最值得保留？还有什么不知道？

后者回答：

> 根据现有证据，下一步最值得做什么？

### 2.2 一个具体示例

假设用户启动任务：

> 研究 AI Agent 安全领域近期的技术发展，重点关注工具调用、权限控制和运行时防护。

**第 0 轮：初始化研究**

系统建立三个核心研究方向：

- A：Agent 工具调用安全。
- B：Agent 权限控制。
- C：Agent 运行时防护。

同时，建立研究目标、允许使用的信息源、时间范围、预算及主题约束。

**第 1 轮：近期信息采集**

系统发现并采集了一批近期文章，完成清洗、去重和相关性评估。

经过分析，得到以下高权重摘要：

```text
本轮研究摘要 R1

1. 工具调用安全是当前研究的重要方向。
2. 现有资料涉及调用前授权、工具执行隔离和输入输出校验。
3. 部分文章引用了较早的权限模型与沙箱设计研究。
4. 目前尚缺乏足够资料比较不同权限控制方案的实际能力。
5. 尚不能判断运行时隔离机制是否普遍覆盖工具执行期间的行为。
```

注意，这只是演示用的研究摘要，不代表真实检索结果。

系统接下来不应该简单地重复搜索「AI Agent Security」，而应该根据摘要产生具体行动。

**第 2 轮：围绕研究缺口继续探索**

系统发现：

- 权限模型的基础设计尚未研究充分。
- 工具执行期间的安全约束缺少证据。
- 不同隔离机制之间缺乏横向比较。

于是生成三个候选行动：

| 行动 | 类型 | 目标 | 优先级 |
|---|---|---|---|
| A1 | 深入研究 | 研究 Agent 工具执行期间的权限约束 | 高 |
| A2 | 历史补充 | 查找权限模型和沙箱机制的基础资料 | 高 |
| A3 | 横向比较 | 比较不同运行时隔离方案的安全边界 | 中 |

系统按照预算选择其中一部分执行。

**第 3 轮：更新研究结论**

假设历史资料揭示了几种不同的权限模型，而近期文章进一步介绍了这些模型在 Agent 系统中的应用。

系统就可以将原先比较模糊的认识，细化为：

- 权限控制发生在哪个阶段？
- 权限是否可以限制到具体工具或具体资源？
- 工具执行过程中是否还会进行约束？
- 是否存在可审计的授权和执行记录？

此时，下一轮研究可以从泛化的「Agent 安全」转向更加具体的技术问题。

这就是迭代研究的价值：**不是每轮都扩大搜索量，而是每轮都减少关键的不确定性。**

## 三、高权重摘要：不要只生成一段总结

如果每轮仅仅生成一段自然语言摘要，下一轮 Agent 很容易遗忘重要细节，或者反复围绕相同的问题搜索。

建议将每轮摘要设计成一个结构化的 **Research Memory（研究记忆）**。

### 3.1 摘要包含哪些内容？

每轮结束后，至少更新以下六类信息：

| 类型 | 含义 | 示例 |
|---|---|---|
| Key Findings | 高价值发现 | 某类权限机制支持调用前校验 |
| Evidence | 支撑发现的证据 | 相关论文、官方文档、技术报告 |
| Knowledge Gaps | 当前知识缺口 | 缺乏执行期间的权限约束资料 |
| New Leads | 新发现的研究线索 | 被多篇文章引用的基础论文 |
| Contradictions | 不同来源的观点差异 | 两种方案对权限边界的描述不同 |
| Next Actions | 下一轮建议行动 | 补充历史资料、开展横向比较 |

其中，`Evidence` 非常重要。

摘要不能只记录结论，还应该记录结论来自哪些文档，以及这些文档能够支持到什么程度。

例如：

```json
{
  "finding_id": "finding_001",
  "statement": "部分 Agent 系统采用调用前的工具权限校验",
  "confidence": 0.91,
  "importance": 0.95,
  "evidence": [
    {
      "document_id": "doc_001",
      "evidence_type": "supports"
    },
    {
      "document_id": "doc_014",
      "evidence_type": "supports"
    }
  ],
  "scope": "当前已采集的文档集合",
  "limitations": [
    "不能据此推断所有 Agent 系统均采用该机制"
  ],
  "follow_up": [
    "调查工具执行期间是否存在持续授权机制"
  ]
}
```

这里的分数和文档 ID 均为示例。

### 3.2 高权重如何计算？

建议将「重要性」与「置信度」分开。

- **重要性**：这个发现对于当前研究目标有多重要。
- **置信度**：当前证据在多大程度上支持这个发现。

一个非常重要、但只有单一来源支持的观点，应该被优先验证，而不是直接被当作确定结论。

建议初期使用以下评分模型：

\[
W = 0.35R + 0.25E + 0.20N + 0.20A
\]

其中：

- \(R\)：与研究目标的相关性。
- \(E\)：证据质量。
- \(N\)：对现有知识的增量价值。
- \(A\)：对后续研究的指导价值。

四项均为 0～100 分。

这只是初始启发式模型，不需要一开始就训练复杂的评分模型。可以让 LLM 给出初始评分，再由确定性规则进行校验和排序。

建议同时保留置信度字段，避免把权重分数误当成事实正确率。

### 3.3 如何避免摘要越来越长？

不建议把历次摘要全部拼接后交给模型。

应该维护三个层次：

**第一层：当前研究状态**

只保存当前最重要的结论、证据、缺口和下一步行动。

**第二层：轮次历史**

保存每轮的完整摘要、决策依据、行动结果和研究状态变化。

**第三层：原始文档库**

保存所有允许保存的文档及其结构化信息。

每轮结束后，将新发现与当前研究状态进行合并：

```text
当前研究状态
     +
本轮新增证据
     │
     ▼
识别新增、重复、冲突和修正
     │
     ▼
更新高权重摘要
     │
     ▼
保留历史版本
```

这样既能避免上下文不断膨胀，又能追溯研究结论是如何形成的。

## 四、研究方向如何自动生成？

建议将下一轮行动分为四种类型，而不是让模型随意产生新关键词。

### 4.1 四种研究行动

| 行动类型 | 目标 | 触发条件 |
|---|---|---|
| Deepen：深入 | 深入研究某个技术问题 | 已发现重要问题，但缺少实现细节或证据 |
| Broaden：扩展 | 扩大研究覆盖范围 | 当前研究过度集中于某些方向 |
| Verify：验证 | 查找原始证据、反例或不同观点 | 关键结论证据不足，或来源之间存在冲突 |
| Backtrack：回溯 | 补充历史研究和基础资料 | 当前技术依赖尚未理解的历史背景 |

例如：

```yaml
next_actions:
  - action_id: action_001
    type: deepen
    topic: "工具执行期间的权限约束"
    reason: "当前文档主要讨论调用前授权"
    priority: 95

  - action_id: action_002
    type: verify
    topic: "运行时沙箱的安全边界"
    reason: "现有资料对隔离能力的描述不一致"
    priority: 90

  - action_id: action_003
    type: backtrack
    topic: "Agent 权限模型的早期研究"
    reason: "近期文章引用了尚未纳入知识库的基础资料"
    priority: 80
```

优先级为演示数据。

### 4.2 研究方向需要经过准入判断

不能让模型提出什么，就立刻执行什么。

建议为每个新行动执行以下检查：

1. 是否直接服务于原始研究目标？
2. 是否属于已允许的研究范围？
3. 是否已有足够资料回答这个问题？
4. 是否与之前的行动高度重复？
5. 是否有明确的预期收益？
6. 是否存在符合规则的可用信息源？
7. 是否满足剩余预算和迭代限制？

通过检查后，行动才会进入待执行队列。

如果一个方向很有价值，但与当前主题关联较弱，可以将它记录为独立的候选研究主题，而不是直接扩展当前任务。

## 五、主题约束：避免迭代越多，研究越偏

这是迭代式研究系统最容易出现的问题。

如果只要求 Agent 不断寻找「值得进一步研究的内容」，它可能从 Agent 安全扩展到 AI 基础设施，再扩展到 GPU、芯片、云计算，最终偏离最初的研究目标。

因此，我建议建立一个独立的 **Research Scope Controller（研究范围控制器）**。

它不负责寻找新信息，而是负责判断新研究方向是否值得纳入当前任务。

### 5.1 建立三层研究范围

每个研究任务都应该有明确的范围定义。

| 范围层级 | 含义 | 处理规则 |
|---|---|---|
| 核心范围 | 用户明确要求研究的主题 | 优先执行 |
| 关联范围 | 为回答核心问题所必需的相关主题 | 满足关联条件后允许扩展 |
| 范围外 | 与核心目标关联较弱的主题 | 不自动展开 |

例如：

```yaml
scope:
  core:
    - Agent 工具调用安全
    - Agent 权限控制
    - Agent 运行时防护

  related:
    - Prompt Injection
    - MCP 安全
    - 沙箱隔离
    - 安全审计

  excluded:
    - 通用大模型训练
    - GPU 性能优化
    - 通用云计算成本分析

  expansion_policy:
    allow_related_topics: true
    require_evidence_for_expansion: true
    allow_new_core_topics: false
```

这意味着，即使研究过程中发现了一个有趣的 GPU 优化项目，只要它与当前研究目标没有明确联系，就不会自动开启新的研究分支。

如果用户确实希望深入 GPU 优化，可以创建独立研究任务，避免污染当前知识库。

### 5.2 使用主题相关性门槛

建议将每个新研究方向与原始目标进行相关性评分。

例如：

| 相关性评分 | 处理策略 |
|---|---|
| 80～100 | 可以进入候选行动队列 |
| 60～79 | 需要说明与核心目标的关联 |
| 40～59 | 暂存为候选线索，不自动执行 |
| 0～39 | 排除出当前研究任务 |

这些区间只是初始配置，需要根据实际效果调整。

此外，不能只根据关键词重合度判断相关性。比如「Agent 安全」和「Agent 运行时沙箱」词汇不同，但后者可能是前者的重要组成部分。

建议结合语义相关性、研究目标匹配度和行动理由进行判断。

### 5.3 建立研究方向预算

建议同时限制研究的深度、广度和运行成本。

```yaml
iteration_policy:
  max_rounds: 8
  max_branch_depth: 3
  max_active_branches: 5

  max_documents_per_round: 50
  max_documents_per_research: 200

  max_requests_per_research: 1000
  max_runtime_minutes: 60

  min_new_information_ratio: 0.10
  min_action_priority: 60

  stop_when_no_progress_rounds: 2
```

以上是示例参数，不是固定标准。

其中：

- `max_rounds`：限制总迭代轮数。
- `max_branch_depth`：限制单条研究分支的延伸深度。
- `max_active_branches`：避免同时展开太多方向。
- `max_documents_per_research`：控制总采集规模。
- `min_new_information_ratio`：避免反复采集高度重复的资料。
- `stop_when_no_progress_rounds`：连续多轮没有明显进展时建议停止。

**建议同时采用硬限制和软限制。**

硬限制由程序强制执行，例如最大轮数、总请求量和运行时间。

软限制由研究规划器判断，例如某个方向是否仍有研究价值、是否偏离主题。

不能把所有约束都交给 LLM 自己判断，否则很难保证执行过程可控。

### 5.4 研究循环的终止条件

每轮完成后，系统应明确选择以下状态之一：

- `CONTINUE`：继续当前研究方向。
- `DEEPEN`：优先深入某个问题。
- `BROADEN`：扩展尚未覆盖的核心方向。
- `VERIFY`：验证重要但证据不足的结论。
- `STOP_COMPLETE`：主要研究目标已经满足。
- `STOP_BUDGET`：预算耗尽。
- `STOP_NO_PROGRESS`：连续多轮没有明显进展。
- `PAUSED_REVIEW`：需要用户确认新的研究方向或访问许可。

这样，研究循环既可以自主推进，也能在必要时停下来。

# 六、分类归档：建立多研究主题共用的本地知识库

第二项调整，我建议采用**研究项目目录 + 全局来源注册表 + 主题内文档归档**的结构。

这里不建议把所有数据都简单塞进一个 CSV，也不建议为每一个研究主题复制一整套 Skill。

更合理的设计是：

- Skill 和采集引擎只有一份。
- 每个研究主题拥有独立的研究目录。
- 来源注册表可以被多个研究项目共享。
- 文档可以根据研究项目分别建立关联。
- HTML 查看器统一读取这些数据。

### 6.3 为什么要把 `state`、`findings` 和 `iterations` 分开？

因为它们分别解决不同问题。

**`state/`：当前研究状态**

记录研究目标、已完成轮数、剩余预算、当前研究分支、待执行行动和停止状态。

程序重新启动时，可以读取这里的数据继续执行，而不必从头开始。

**`findings/`：研究发现与证据**

记录跨轮次积累的重要发现，以及每个发现对应的文档证据。

同一个发现可能被多轮研究不断补充或修正，因此它不应该只存在于某轮摘要中。

**`iterations/`：研究过程历史**

记录每轮做了什么、为什么这样做、采集了什么、产生了哪些新发现，以及为什么决定继续或停止。

这有助于排查问题。例如，当研究方向发生偏移时，可以直接检查是哪一轮引入了新的分支，以及当时的决策依据是什么。

### 6.4 如何处理跨项目复用？

建议为来源和文档分配稳定的 ID。

例如：

```text
source_id: src_8f12a1
document_id: doc_93bc21
research_id: res_20261025_001
finding_id: find_4a921d
```

同一个来源可以被多个研究项目使用。

同一篇文档也可能与多个研究主题相关，但不必因此复制多份原始内容。可以在全局文档索引中保存文档，在各项目中保存与它的关联、评分和研究上下文。

需要注意，**文档的相关性评分应该允许按研究项目分别计算**。

一篇关于 Agent 沙箱的文章，对 Agent 安全研究可能高度相关，对通用 AI 产品商业模式研究则未必如此。

### 6.5 目录还是数据库？

我建议采用混合方案：

| 数据类型 | 推荐存储方式 | 原因 |
|---|---|---|
| 研究配置 | YAML | 方便人工编辑 |
| 来源注册表 | JSONL | 易于追加、迁移 |
| 文档元数据 | JSONL + CSV | 程序处理与人工查看兼顾 |
| 原文内容 | 独立文件 | 避免结构化数据过大 |
| 研究状态 | JSON | 方便恢复任务 |
| 每轮研究历史 | JSONL / JSON | 便于追踪过程 |
| 大量文档的检索索引 | SQLite | 支持查询和唯一约束 |
| 报告 | Markdown / HTML | 易于阅读与分享 |

第一版完全可以不引入 SQLite。

但如果后续需要跨项目查询、按时间和相关性筛选大量文档，SQLite 会比反复扫描 JSONL 文件更合适。

# 九、建议的实现顺序

为了避免一次性实现过多能力，我建议按以下顺序开发。

| 阶段 | 重点 | 交付物 |
|---|---|---|
| Phase 1 | 合规采集与结构化归档 | 可运行的基础 Skill |
| Phase 2 | 研究循环与高权重摘要 | ReAct 式研究引擎 |
| Phase 3 | 主题约束与预算控制 | 可控的多轮研究 |
| Phase 4 | 分类目录与本地检索 | 多主题知识库 |
| Phase 5 | 静态 HTML 查看器 | 可浏览的研究界面 |
| Phase 6 | 增量采集与研究恢复 | 可长期使用的研究工具 |

其中，Phase 1～3 是核心能力，Phase 4～5 是知识管理与展示能力，Phase 6 则是稳定性增强。

## 第一版应该完成什么？

建议第一版实现以下最小闭环：

1. 用户指定研究主题和目标。
2. Skill 发现候选来源，并执行合规检查。
3. 用户确认来源后，优先采集近期信息。
4. 每轮结束后生成结构化高权重摘要。
5. 根据研究缺口生成下一轮行动。
6. 经过主题约束和预算检查后，继续或停止。
7. 所有结果按研究主题归档。
8. 生成 CSV、Markdown 和简单 HTML 页面。

暂时不需要：

- 多 Agent 协作。
- 独立数据库服务器。
- 复杂的知识图谱。
- 自动化网页操作和绕过访问限制。
- 大规模向量数据库。
- 实时监控和复杂可视化。

## 十、最终设计决策

我认为这次调整后，项目的核心已经不再是「一个能爬取网站的 Skill」，而是一个轻量级的**迭代式行业研究与知识沉淀工具**。

最终建议确定以下四项核心机制：

**1. Research Loop：研究循环**

每轮必须产出新的研究摘要、研究缺口和下一步行动，而不只是执行抓取。

**2. Scope Controller：主题约束**

所有新方向都必须经过相关性、预算和范围检查，避免研究不断扩张。

**3. Research Archive：分类知识库**

每个主题独立归档，来源、文档、研究发现和迭代历史可以关联，同时保留稳定的文件结构。

**4. Static Viewer：本地 HTML 查看器**

将已有研究成果转化为可导航、可筛选、可追溯的静态网页，不需要独立后台服务。

最终形成的使用体验应该是：

> 我告诉 Skill 想研究什么，它先发现和筛选信息源，然后逐轮采集、总结、发现新的研究问题，并在主题约束下持续推进。所有资料和研究过程都会被保存下来，之后我可以通过本地目录、CSV、Markdown 或 HTML 页面继续查看、搜索和复用。

**最关键的设计原则是：每轮迭代都必须产生可验证的信息增量，或者明确说明为什么需要进一步验证；如果既没有新的可靠证据，也没有值得执行的下一步行动，就应该停止，而不是为了继续运行而继续爬取。**

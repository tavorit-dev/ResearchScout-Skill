## 一、意图与理由

### 1.1 这个 Skill 是什么

**Research Scout（研究侦察员）** 是一个开源 Skill，面向行业研究、技术调研、竞品分析和趋势追踪，提供**合规的信息发现、线索追踪与来源探索**能力。

它不是通用爬虫，也不是一次性搜索工具。它建立一套可以反复执行、持续积累的工作流：

> 定义研究范围 → 发现信息源 → 合规检查 → 来源确认 → 多轮迭代研究 → 结构化沉淀 → 生成下一步行动

最终交付的不是一份看完就丢的网页列表，而是一个**按主题独立归档、可检索、可复用、能够反哺后续研究的本地知识库**。

### 1.2 为什么是"侦察"而不是"采集"

侦察员不负责把东西搬回来，负责探路、摸清地形、标出哪里有东西、哪里不能进。这个名字对应三块核心能力：

- **哪里不能进** → 合规闸门
- **下一步往哪探** → 研究循环
- **把侦察结果标在地图上** → 分类归档

### 1.3 为什么现在做

现有工具要么是重型爬虫框架（配置成本高，不管研究语义），要么是 SaaS 研究服务（数据不在本地，不可追溯）。中间地带——**本地优先、合规优先、按主题持续积累**——是空的。

### 1.4 成功的样子

一个陌生人在自己的机器上安装这个 Skill，说一句"研究 AI Agent 安全"，得到：

1. 一份经过合规检查的候选来源清单，并清楚知道每个来源能不能采、依据是什么；
2. 一个多轮推进的研究过程，每轮产出带证据的结构化发现，并自己生成下一步该查什么；
3. 一个按主题归档在本地目录里的知识库，可以浏览、检索、导出。

### 1.5 目标读者

主要读者是**中文技术研究者**：需要长期跟踪某个技术领域、愿意在本地跑工具、对数据留在自己机器上有要求的人。

不是"对 AI 好奇的普通用户"——这决定了首次体验可以要求用户理解"来源""合规""轮次"这些概念，但**不能要求用户先读文档或改配置才能跑通**。

## 二、目标与非目标

### 2.1 目标

| 编号 | 目标 |
|---|---|
| G1 | 合规检查先于采集，且是强制独立模块，任何来源、任何轮次、任何扩展层级都必须经过 |
| G2 | 研究循环每轮产出结构化的研究记忆（发现/证据/缺口/线索/冲突/下一步），而不是一段自然语言总结 |
| G3 | 结果按研究主题独立归档，结构稳定，可被程序读取、可被人工浏览 |
| G4 | 全新安装、零额外配置的情况下可以跑通完整闭环（不需要用户自备 API Key；但需要一个能驱动 Skill 的 LLM 宿主） |
| G5 | 其他人能安装使用：无硬编码路径、无个人假设、无内置密钥 |
| G6 | 每一轮都产生可验证的信息增量，否则停止 |

### 2.2 非目标（v1 明确不做）

- 不做独立数据库服务器（SQLite 延后到有跨项目查询需求时）
- 不做多 Agent 编排
- 不做知识图谱
- 不做向量数据库与语义检索
- 不做常驻 Web 服务
- 不做自动化网页操作
- 不做定期/定时采集任务

### 2.3 反目标（技术上能跑通，但算失败）

| 反目标 | 为什么算失败 |
|---|---|
| A1 | 采集绕过了合规闸门，或为了跑通而放宽闸门 | 合规是这个项目能开源的前提，不是可选项 |
| A2 | 研究循环在预算内跑偏主题（Agent 安全 → GPU → 芯片） | 没有范围控制，产出越多越没用 |
| A3 | 用户第一次运行看到的是报错或空白，而不是候选清单 | 陌生人会在这一步卸载 |
| A4 | 模型凭记忆编造的来源 URL 被当成已确认来源直接采集 | 会真实请求不存在的地址，且污染知识库 |
| A5 | 跨文档综合结论被写成某篇原文的事实 | 违反可追溯性，多轮后错误会被放大 |
| A6 | 每轮摘要不断拼接，上下文无限膨胀 | 几轮之后模型开始遗忘和重复 |

## 三、约束

### 3.1 技术约束

| 约束 | 说明 |
|---|---|
| C1 | 宿主无关：`SKILL.md` 不写 Claude Code 专有的 frontmatter 或调用方式 |
| C2 | Python 标准库优先；引入第三方依赖须在 `requirements.txt` 声明并说明理由 |
| C3 | 确定性逻辑（合规检查、去重、URL 规范化、预算控制）的测试不得联网 |
| C4 | 搜索能力必须可插拔，Skill 不假设自己天然拥有全网搜索能力 |
| C5 | 本地文件系统是唯一必需的基础设施 |
| C6 | 归档路径使用英文 slug，避免中文路径的编码问题 |
| C7 | **必须有 LLM 宿主**。Skill 由宿主 Agent 驱动，LLM 能力来自宿主，不需要用户自备 API Key |
| C8 | 脚本是**单轮执行器**，不是自循环器。跨轮控制权在宿主 Agent 手中 |

### 3.2 语言约束

| 文件 | 语言 |
|---|---|
| `SKILL.md`、`schemas/*.json` | 英文 |
| `README.md` | 简体中文（默认版本） |
| `README.en.md` | 英文（与中文版章节结构一致） |
| `CLAUDE.md`、`docs/*.md` | 中文 |
| 面向用户的文档 | 中文 |
| `archive/` 下的研究产物（`summaries/*.md`、`reports/*.md`） | 中文 |
| Python 代码标识符 | 英文；注释与 docstring 英文 |
| 代码标识符、JSON 字段名、状态值、行动类型 | 英文，不翻译 |

与用户交流默认使用简体中文，此约定已固化。

### 3.3 合规约束

见第六章。合规约束不是"最佳实践"，是硬性要求。

### 3.4 资源约束

- 无预算购买搜索 API，因此搜索 provider 不设默认值，必须支持零成本路径。
- 单人维护，因此不引入需要长期运维的组件。

## 四、v1 范围

### 4.1 三块核心能力

| 能力 | 职责 | 交付 |
|---|---|---|
| **合规闸门** | 判断来源是否允许拟采用的访问方式 | 合规状态 + 检查依据 |
| **研究循环** | 每轮行动、观察、提炼、决策 | 研究记忆 + 下一步行动 |
| **分类归档** | 按主题分类、去重、结构化保存 | 可浏览可检索的本地知识库 |

Markdown 报告与 CSV 导出算归档的**视图**，不单独计为一块能力。

### 4.2 明确延后

| 延后项 | 延后到什么程度 |
|---|---|
| 范围控制器 | 只保留 `research.yaml` 的 `core`/`related`/`excluded` 静态列表 + 硬校验。不做相关性打分、不做自动范围推断 |
| 静态 HTML 查看器 | v1 不实现。归档结构必须为它留好接口，Phase 5 可直接构建 |
| SQLite | v1 不引入。数据量增长后再加 |
| 增量采集与研究恢复 | 归档结构必须支持断点恢复（`state/`），但 v1 不实现跨运行的自动续跑 |

### 4.3 实现顺序

| 阶段 | 重点 | 交付物 |
|---|---|---|
| Phase 1 | 合规采集与结构化归档 | 可运行的基础 Skill |
| Phase 2 | 研究循环与高权重摘要 | ReAct 式研究引擎 |
| Phase 3 | 主题约束与预算控制 | 可控的多轮研究 |
| Phase 4 | 分类目录与本地检索 | 多主题知识库 |
| Phase 5 | 静态 HTML 查看器 | 可浏览的研究界面 |
| Phase 6 | 增量采集与研究恢复 | 可长期使用的研究工具 |

v1 = Phase 1 + Phase 2 的核心 + Phase 3 的静态范围校验部分 + Phase 4 的归档结构。Phase 5、6 不在 v1。

## 五、驱动模型（本设计的核心决定）

### 5.1 零 API Key ≠ 零 LLM

**这个 Skill 必须有 LLM 才能运转。** 它由宿主 Agent（Claude Code 等）驱动，LLM 能力来自宿主，用户不需要自备任何 API Key。

因此「全新安装即可用」的正确表述是**零额外配置**，而不是「不依赖 LLM」。用户需要的是一个能驱动 Skill 的宿主环境，这在他安装 Skill 时已经具备。

### 5.2 脚本是单轮执行器，不是循环器

`research_loop.py` **执行一轮**，不执行八轮。跨轮控制权在宿主 Agent 手中。

原因：六步中第 2、3、4、5 步都需要 LLM，而 Python 脚本调不到 LLM。如果脚本试图自己跑完整个循环，就必须内置 API Key——这与零额外配置冲突。

### 5.3 每步由谁执行

| 步骤 | 执行者 | 说明 |
|---|---|---|
| 1 Action 检索采集 | 脚本 | 确定性：检索、合规检查、抓取、清洗、去重、入库 |
| 2 Observation 评估 | **Agent** | 脚本准备候选与元数据，Agent 判断质量、相关性与价值 |
| 3 Evidence Extraction | **Agent** | Agent 从文档提炼事实与证据，脚本做 Schema 校验 |
| 4 Reflection 更新研究记忆 | **Agent** | Agent 判断认识是否变化，脚本负责与当前状态合并 |
| 5 Next Action 生成行动 | **Agent** | Agent 提出候选行动，脚本做准入校验与范围硬校验 |
| 6 Persist 持久化 | 脚本 | 确定性：写入 `state/`、`findings/`、`iterations/`、`summaries/` |

**原则：LLM 负责语义判断，脚本负责状态、校验与写入。** 脚本永远不替 Agent 判断语义，Agent 永远不直接写文件。

### 5.4 `SKILL.md` 是驱动协议

因为控制权在宿主，`SKILL.md` 不只是说明文档，而是**驱动协议**：它规定 Agent 每轮按什么顺序调用哪些脚本、脚本返回什么、Agent 必须回填什么字段。

这是 v1 最重要的交付物之一。脚本是 Agent 的手，`SKILL.md` 是节拍。

### 5.5 无 LLM 宿主时的行为

**不定义降级路径，明确报错。**

`research_loop.py --check-env` 在检测到非 Agent 环境时直接说明「本 Skill 需要 LLM 宿主驱动，无法独立运行」并退出。

假装能在无 LLM 环境下工作，比诚实报错更糟——它会产出一堆看似成功、实则没有语义判断的中间数据。

### 5.6 每轮之间的交还协议

脚本执行完第 1 步后，必须向宿主返回**结构化交接包**，包含：

- 本轮新增文档的 ID 列表与元数据
- 需要 Agent 判断的候选集合
- 当前研究状态摘要
- 本轮剩余预算

Agent 完成第 2～5 步后，把结果按 Schema 回填给脚本执行第 6 步。**交还点必须是显式的、可校验的**，不能依赖 Agent 记住上下文。

## 六、合规闸门

### 6.1 定位

合规闸门是**独立模块**，不是散落在采集代码里的几个判断条件。任何来源、任何轮次、任何扩展层级都必须先过闸门。

### 6.2 状态

```text
DISCOVERED → CHECKING ─┬─► ALLOWED
                       ├─► BLOCKED
                       ├─► REVIEW_REQUIRED
                       └─► ERROR
```

| 状态 | 含义 |
|---|---|
| `ALLOWED` | 已完成必要检查，当前采集方式符合已确认的规则 |
| `BLOCKED` | 发现明确的禁止规则或不允许的访问方式 |
| `REVIEW_REQUIRED` | 存在歧义，或尚未取得必要授权 |
| `ERROR` | 检查因网络故障等原因未能完成 |

**`BLOCKED` 与 `ERROR` 必须区分。** 网络故障不代表网站允许抓取，不得通过重试绕过。

### 6.3 检查维度

| 检查项 | 内容 | 失败处理 |
|---|---|---|
| robots.txt | 目标路径是否被禁止 | 禁止路径直接 `BLOCKED` |
| 网站使用条款 | 是否限制自动化访问、复制或存储 | 不明确时 `REVIEW_REQUIRED` |
| API / Feed 条款 | 是否允许使用、调用额度 | 不符合约束则停止 |
| 技术访问控制 | 是否要求登录、授权或存在访问限制 | 无授权时不继续访问 |

### 6.4 保守默认（本设计的明确决定）

| 情形 | 处理 |
|---|---|
| robots.txt 返回 5xx 或网络故障 | `ERROR`，暂停该来源，**不默认放行** |
| robots.txt 404（不存在） | 视为无禁止规则，但记录依据 |
| 使用条款无法判定或页面不可达 | `REVIEW_REQUIRED` |
| 条款明确禁止自动化访问 | `BLOCKED` |
| 遇到登录墙、验证码、访问控制 | `BLOCKED`，停止自动采集 |

**宁可多停一次，也不默认放行。** 这是本项目相对于普通爬虫的核心差异。

### 6.5 `REVIEW_REQUIRED` 的解除（本设计的明确决定）

`REVIEW_REQUIRED` 不会自己变成 `ALLOWED`。必须由用户显式授权，程序记录授权后才放行。

授权记录写入 `archive/registry/source_policies.jsonl`，字段：

| 字段 | 说明 |
|---|---|
| `source_id` | 来源 ID |
| `resolved_status` | 用户判定为 `ALLOWED` 还是 `BLOCKED` |
| `resolved_by` | `user` |
| `resolved_at` | 授权时间 |
| `reason` | 用户给出的理由（可空） |
| `scope` | 授权范围：`paths`、`access_method`、`expires_at` |
| `check_record_ref` | 对应的检查记录 ID |

**用户授权不等于永久放行。** 授权带 `expires_at` 与路径/方式范围；超出范围或过期后重新进入 `REVIEW_REQUIRED`。

`SKILL.md` 必须提供一条明确路径让用户完成这个授权动作，不能要求用户手改 JSON。

### 6.6 时效性

合规结果具有时效性。每次实际采集前验证缓存的检查结果是否仍然有效；规则变化或超过有效期时重新检查。

### 6.7 检查记录

每条检查记录包含 `source_id`、`domain`、`checked_at`、各项检查状态、`access_method`、`compliance_status`、`allowed_paths`、`request_rate_limit`、`evidence[]`、`notes`。

`evidence` 必须记录**依据来源**（robots.txt 的 URL、条款页面的 URL），使检查结果可复核。

### 6.8 边界声明

合规状态是**产品状态，不是法律意义上的许可认定**。`SKILL.md` 与 `README` 必须明确说明这一点，不能让用户误以为 `ALLOWED` 等于取得了法律授权。

## 七、研究循环

### 7.1 六个步骤

每轮固定执行：

| 步骤 | 任务 | 输出 |
|---|---|---|
| 1 Action | 按当前研究计划执行检索与采集 | 新增文档 |
| 2 Observation | 评估新增文档的质量、相关性与价值 | 观察记录 |
| 3 Evidence Extraction | 提取重要事实、技术方案与证据 | 证据集合 |
| 4 Reflection | 更新研究记忆，判断已有认识是否变化 | 本轮摘要 |
| 5 Next Action | 判断深入、扩展、验证还是停止 | 下一轮行动计划 |
| 6 Persist | 保存全部结果与状态 | 可恢复的研究状态 |

### 7.2 研究记忆（Research Memory）

每轮更新六类信息：

| 类型 | 含义 |
|---|---|
| Key Findings | 高价值发现 |
| Evidence | 支撑发现的证据 |
| Knowledge Gaps | 当前知识缺口 |
| New Leads | 新发现的研究线索 |
| Contradictions | 不同来源的观点差异 |
| Next Actions | 下一轮建议行动 |

**分三层维护，避免上下文膨胀：**

1. **当前研究状态**：只保存当前最重要的结论、证据、缺口与下一步行动
2. **轮次历史**：每轮的完整摘要、决策依据、行动结果与状态变化
3. **原始文档库**：所有允许保存的文档及其结构化信息

每轮结束后，把新证据与当前状态合并：识别新增 / 重复 / 冲突 / 修正 → 更新研究记忆 → 保留历史版本。

**不要把历次摘要全部拼接后交给模型。**

### 7.3 发现的结构

每个发现（finding）包含：

| 字段 | 说明 |
|---|---|
| `finding_id` | 唯一 ID |
| `statement` | 发现陈述 |
| `confidence` | 置信度：当前证据在多大程度上支持该发现 |
| `importance` | 重要性：对当前研究目标有多重要 |
| `evidence[]` | 支撑证据，每条含 `document_id` 与 `evidence_type`（`supports` / `contradicts` / `partially_supports`） |
| `scope` | 该发现适用的范围 |
| `limitations[]` | 不能据此推断什么 |
| `follow_up[]` | 需要进一步查证的问题 |

**重要性与置信度必须分开。** 一个非常重要、但只有单一来源支持的观点，应被优先验证，而不是直接当作确定结论。

### 7.4 高权重计算

\[
W = 0.35R + 0.25E + 0.20N + 0.20A
\]

- \(R\)：与研究目标的相关性
- \(E\)：证据质量
- \(N\)：对现有知识的增量价值
- \(A\)：对后续研究的指导价值

四项均 0～100 分。由 LLM 给出初始评分，确定性规则做校验与排序。

**保留 `confidence` 字段，不得把权重分数当作事实正确率。**

### 7.5 四种研究行动

| 类型 | 目标 | 触发条件 |
|---|---|---|
| `deepen` | 深入研究某个技术问题 | 已发现重要问题，但缺少实现细节或证据 |
| `broaden` | 扩大研究覆盖范围 | 当前研究过度集中于某些方向 |
| `verify` | 查找原始证据、反例或不同观点 | 关键结论证据不足，或来源之间存在冲突 |
| `backtrack` | 补充历史研究和基础资料 | 当前技术依赖尚未理解的历史背景 |

**每种行动都带时间窗口**（本设计的明确决定），默认值：

| 行动类型 | 默认时间窗口 |
|---|---|
| `deepen` | 近 180 天 |
| `broaden` | 近 180 天 |
| `verify` | 不限（需要找到原始证据，可能很旧） |
| `backtrack` | 近 5 年（`historical_days: 1825`） |

时间窗口是行动的必填字段，由 Agent 给出，可被用户在 `research.yaml` 覆盖。**没有时间边界的 `backtrack` 会去搜整个互联网的历史资料**，必须显式限定。

### 7.6 历史资料准入规则

时效性只决定排序，**不决定历史资料有没有资格被收录**。

满足以下任一条件的历史资料允许进入补充队列：

1. 直接回答核心研究问题
2. 被多个高相关来源引用
3. 是某项技术的原始论文或权威规范
4. 是理解近期技术进展所必需的基础资料

历史资料进入队列后，仍须经过相关性评估与合规检查。

### 7.7 行动准入检查

每个候选行动执行以下检查，全部通过才进入待执行队列：

1. 是否直接服务于原始研究目标？
2. 是否属于 `research.yaml` 中 `core` 或 `related` 范围？
3. 是否属于 `excluded` 范围？（若是，直接拒绝）
4. 是否已有足够资料回答这个问题？
5. 是否与之前的行动高度重复？
6. 是否有明确的预期收益？
7. 是否存在合规可用的信息源？
8. 是否满足剩余预算与迭代限制？

### 7.8 静态范围校验（本设计的明确决定）

v1 不实现完整的范围控制器。替代方案：

- `research.yaml` 中显式定义 `core` / `related` / `excluded` 三个列表
- 每个候选行动必须通过列表归属硬校验
- `related` 范围的行动必须说明与核心目标的关联，否则降级为候选线索，不自动执行
- `excluded` 范围的行动直接拒绝，并记录为独立候选研究主题

**「说明关联」由程序做形式校验，不做语义校验**（本设计的明确决定）：`related` 范围的行动必须带非空的 `scope_justification` 字段，程序只检查非空。语义上是否真的相关由 Agent 判断，程序不替它判断——符合「不让 LLM 自觉」的原则，同时不引入语义打分的复杂度。

**不做相关性打分，不做自动范围推断。** 这是有意的取舍：用最便宜的方式买到大部分安全性，代价是范围需要用户显式声明。

**如果范围列表为空**：首次运行时由 LLM 根据研究目标生成一份建议范围，明确标注为"建议，请确认"，用户确认后写入 `research.yaml`。不得在未确认的情况下用建议范围做硬校验。

### 7.9 终止状态

每轮完成后明确选择其一：

- `CONTINUE`：继续当前研究方向
- `DEEPEN`：优先深入某个问题
- `BROADEN`：扩展尚未覆盖的核心方向
- `VERIFY`：验证重要但证据不足的结论
- `STOP_COMPLETE`：主要研究目标已满足
- `STOP_BUDGET`：预算耗尽
- `STOP_NO_PROGRESS`：连续多轮没有明显进展
- `PAUSED_REVIEW`：需要用户确认新的研究方向或访问许可

### 7.10 预算与硬限制

```yaml
iteration_policy:
  max_rounds: 8
  max_branch_depth: 3
  max_active_branches: 5
  max_documents_per_round: 50
  max_documents_per_research: 200
  max_requests_per_research: 1000
  max_runtime_minutes: 60
  min_new_information_ratio: 0.10
  min_action_priority: 60
  stop_when_no_progress_rounds: 2
```

**硬限制由程序强制**（最大轮数、总请求量、运行时长），**软限制由研究规划器判断**（方向价值、是否偏离主题）。不得把所有约束交给 LLM 自行判断。

### 7.11 终止原则

> 每轮迭代都必须产生可验证的信息增量，或者明确说明为什么需要进一步验证；如果既没有新的可靠证据，也没有值得执行的下一步行动，就应该停止，而不是为了继续运行而继续爬取。

## 八、来源发现与搜索 provider

### 8.1 可插拔 provider 接口

Skill 不假设自己天然拥有全网搜索能力。搜索接口是可配置的依赖。

**契约（单个函数）：**

```python
def search(query: str, time_range: TimeRange, limit: int) -> list[CandidateSource]:
    """返回候选来源列表。不执行采集，不做合规判断。"""
```

### 8.2 v1 提供的两个实现

| provider | 行为 | 成本 |
|---|---|---|
| `manual` | 用户粘贴候选 URL，程序解析域名与来源类型 | 零 |
| `llm` | 由模型根据研究目标给出候选来源 | 零 |

**不设默认 provider。** 首次运行时若未配置，走 `llm` 路径并带明确标注（见 8.3）。

第三方 provider（Brave、Serper、Tavily、Google CSE 等）通过配置文件挂载，v1 只定义接口，不内置实现。

### 8.3 首次体验（本设计的明确决定）

全新安装、零额外配置时（LLM 来自宿主 Agent，用户不需要自备 Key），用户说"研究 AI Agent 安全"，**期望第一眼看到**：

1. **一份候选来源清单**——让用户立刻有东西可看、可判断；
2. **同时说明这份清单的来源与局限**——它来自模型知识，未经任何验证。

清单中的每个条目必须标注为**待验证的候选**，并明确提示：

> 这些来源来自模型知识，可能已失效或不存在。确认后才会进行合规检查，合规检查会真实请求这些地址。

**绝不能把模型凭记忆报出的来源当作已确认来源直接采集。** 这是反目标 A4。

候选清单同时提供三条路径：

- 粘贴自己的候选 URL
- 配置第三方搜索 provider
- 从当前候选清单中挑选

### 8.4 模型给出来源的验证路径

因为 `llm` provider 的来源来自模型记忆，必须有一条**明确的验证动作**把它变成可信来源：

1. 来源以 `discovery_verified: false` 进入候选清单
2. 用户确认后，程序对 `base_url` 做**可达性检查**（HTTP 请求，遵守 10.4 的限速）
3. 可达 → 进入合规检查流程；不可达 → 标记为 `UNREACHABLE`，不进入合规检查，向用户报告

**可达性检查与合规检查是两件事。** 可达性检查只回答"这个地址存在吗"，不回答"允许采集吗"。顺序是先可达、后合规。

### 8.5 候选来源字段

| 字段 | 说明 |
|---|---|
| `source_id` | 来源唯一 ID |
| `source_name` | 来源名称 |
| `base_url` | 网站主地址 |
| `source_type` | 官方网站、RSS、API、论文平台等 |
| `industry_tags` | 行业标签 |
| `topic_tags` | 研究主题标签 |
| `authority_level` | 来源权威性评估 |
| `discovery_method` | 搜索引擎、人工添加、关联发现、模型知识等 |
| `discovery_verified` | 该来源是否经过验证（模型给出的为 `false`） |
| `robots_url` | robots.txt 地址 |
| `terms_url` | 使用条款地址 |
| `compliance_status` | 合规检查状态 |
| `allowed_paths` | 允许访问的路径范围 |
| `access_method` | API、RSS、网页等 |
| `last_checked_at` | 最近检查时间 |
| `selection_status` | 待选择、已选中、已排除 |

**来源权威性与文档相关性分开评分。** 高权威来源的一篇不相关文章，不应仅因来源权威而排在前面。

### 8.6 三阶段分离

**信息源发现、来源选择、正文采集是三个独立阶段。**

不允许搜索到一个网站就立即对它递归爬取。这既难以控制访问范围，也让研究结果缺乏明确的来源管理。

### 8.7 来源选择两种模式

| 模式 | 行为 |
|---|---|
| 交互式 | 展示可用 / 待确认 / 禁止采集的来源，由用户选择本轮采集清单 |
| 自动化 | 用户预先设定允许的来源集合与策略，Skill 自动选择符合策略的来源 |

自动化模式遇到新域名、规则变化或不确定的许可状态时，暂停相应任务。

### 9.3 为什么 `state` / `findings` / `iterations` 分开

| 目录 | 解决的问题 |
|---|---|
| `state/` | 当前研究状态：目标、已完成轮数、剩余预算、当前分支、待执行行动、停止状态。程序重启后可据此恢复 |
| `findings/` | 跨轮次积累的重要发现及其文档证据。同一发现可能被多轮补充或修正，不应只存在于某轮摘要中 |
| `iterations/` | 研究过程历史：每轮做了什么、为什么、采集了什么、产生哪些新发现、为何决定继续或停止 |

排查问题时（例如研究方向发生偏移），可以直接检查是哪一轮引入了新分支、当时的决策依据是什么。

### 9.4 跨项目复用

稳定 ID：

```text
source_id:   src_8f12a1
document_id: doc_93bc21
research_id: res_20261025_001
finding_id:  find_4a921d
```

- 同一来源可被多个研究项目使用 → 放在 `archive/registry/`
- 同一文档可能关联多个研究主题，但**不复制多份原始内容**
- **文档的相关性评分按研究项目分别计算**：一篇 Agent 沙箱文章对 Agent 安全研究高度相关，对通用 AI 产品研究未必

### 9.5 存储方式

| 数据类型 | 方式 | 原因 |
|---|---|---|
| 研究配置 | YAML | 方便人工编辑 |
| 来源注册表 | JSONL | 易于追加、迁移 |
| 文档元数据 | JSONL + CSV | 程序处理与人工查看兼顾 |
| 原文内容 | 独立文件 | 避免结构化数据过大 |
| 研究状态 | JSON | 方便恢复任务 |
| 每轮历史 | JSONL / JSON | 便于追踪过程 |
| 报告 | Markdown | 易于阅读与分享 |

v1 不引入 SQLite。

### 9.6 原文保存策略

区分**原文地址**与**原文内容**。原文地址是追溯来源所必需的，优先保存。原文内容根据条款、许可范围、版权决定是否保存及保存多少。

| 模式 | 保存内容 | 适用场景 |
|---|---|---|
| `reference` | 元数据、摘要、原文地址 | 对正文保存有严格限制的来源 |
| `extracted` | 元数据、允许保存的正文提取结果 | 许可范围明确的公开资料 |
| `full_archive` | 完整正文、元数据、内容指纹 | 允许完整归档的自有或授权资料 |

不允许保存完整原文时，只保留原文链接、必要元数据和符合许可的简短摘要。

### 9.7 文档数据模型

`document_id`、`source_id`、`source_name`、`source_url`、`title`、`author`、`published_at`、`updated_at`、`crawled_at`、`first_seen_at`、`canonical_url`、`content_type`、`language`、`industry_tags`、`topic_tags`、`summary`、`key_points`、`entities`、`relevance_score`、`authority_score`、`freshness_score`、`novelty_score`、`content_hash`、`raw_content_ref`、`collection_method`、`compliance_record_id`、`crawl_status`、`retention_mode`、`date_confidence`、`round_discovered`、`attempt_count`。

不作为统一 CSV 强制包含全部字段；CSV 只导出适合表格展示的字段。

补充字段说明：

| 字段 | 说明 |
|---|---|
| `date_confidence` | 发布时间来源与置信度。日期未知时 `published_at` 留空，此字段记录推断依据，**不让模型猜日期** |
| `round_discovered` | 该文档在哪一轮被发现，用于迭代历史追溯 |
| `attempt_count` | 采集尝试次数，用于失败重试与终止判断 |

### 9.8 三层内容分离

| 层次 | 内容 |
|---|---|
| 第一层 原始记录 | 采集到的正文、标题、原文地址、来源、发布时间 |
| 第二层 文档分析 | 摘要、主题标签、关键实体、技术方案、优缺点、引用关系 |
| 第三层 研究结论 | 跨文档综合得出的趋势、技术比较、争议、研究空白、后续问题 |

**三者不得混为一谈。** 跨文档综合结论不得写成任何单篇文章的原文事实，所有结论保留可追溯的 `document_id`。

## 十、关键实现细节

### 10.1 去重三层

1. **URL 去重**：移除确认无意义的跟踪参数，规范化 URL
2. **内容指纹去重**：正文哈希识别内容完全相同的记录
3. **语义近似去重**：识别转载、改写、相似内容

语义近似去重需谨慎：不同来源可能提供不同证据和观点，不得因主题相同就合并。

### 10.2 时间字段

`published_at`、`updated_at`、`crawled_at`、`first_seen_at` 分开保存。

部分网站不提供发布时间，或修改文章而不更新发布日期。**未知字段留空，并记录日期来源与置信度，不让模型猜日期。**

### 10.3 文档状态机

```text
DISCOVERED → QUEUED → FETCHED → EXTRACTED → ANALYZED → PERSISTED
```

失败状态单独管理，记录失败原因、重试次数、下次允许重试时间。

**轮次结束时的未完成文档**（本设计的明确决定）：一轮结束时仍停在 `QUEUED`、`FETCHED` 或 `EXTRACTED` 的文档**保留，下一轮优先处理**，不丢弃。

处理顺序：未完成文档 → 新发现文档 → 内容变化文档 → 可重试失败文档 → 用户要求重新分析的文档。

`attempt_count` 超过阈值（默认 3）的文档转入永久失败，不再重试，并在报告中列出，避免单篇文档反复消耗预算。

下一轮优先处理：未完成任务、新发现文档、内容变化文档、可重试文档、用户要求重新分析的文档。**不重新下载整个历史集合。**

### 10.4 请求限速与异常处理

- 每域名独立并发限制
- 可配置请求间隔
- 超时与响应体大小限制
- 429、5xx 有限重试，尊重 `Retry-After`
- robots.txt 检查结果缓存
- 遇到明确禁止、登录墙、验证码、访问控制时停止自动采集
- 总请求数、文档数、运行时长预算

**不得通过更换 User-Agent、代理或其他技术手段绕过网站明确表达的访问限制。**

### 10.5 提示注入防护

网页正文一律视为**不可信输入**。

1. 网页内容与系统指令、工具参数严格隔离
2. 不允许网页内容直接决定本地命令执行、文件读取或网络请求
3. 后续检索任务只能从经过验证的结构化字段生成
4. 对 URL 执行域名与访问规则检查，避免模型生成的链接绕过合规闸门
5. 对 LLM 输出做 Schema 校验，限制后续动作范围

考虑到本项目可能被用于安全研究，这部分是基础能力，不是后续优化项。

### 10.6 摘要质量控制

每篇文档的摘要回答四个问题：

1. 这篇文章讲了什么？
2. 它提出了什么技术、观点或发现？
3. 它为什么与当前研究主题有关？
4. 它能为后续研究提供什么线索？

摘要生成后做一次字段完整性与来源一致性检查，**尤其避免模型把自己的推断写成文章明确提出的事实**。

## 十一、留给实现者的决定

以下是本设计**有意不指定**、留给实现者的部分：

1. **CLI 具体形态**：`SKILL.md` 中的命令是逻辑接口（`init` / `sources` / `check` / `approve` / `collect` / `expand` / `analyze` / `search` / `export` / `status`），不要求必须实现为 CLI 子命令。实现者可选择脚本参数或统一入口。
2. **配置文件的具体 schema**：`default.yaml` / `scoring.yaml` / `iteration.yaml` 的字段划分由实现者决定，只要覆盖本文档出现的参数。
3. **LLM 调用的接入方式**：Skill 由宿主 Agent 驱动，LLM 能力的调用方式取决于宿主，本设计不规定。
4. **内容提取的具体实现**：正文提取的库选择、规则策略由实现者决定，但必须满足 10.6 的质量要求。
5. **评分权重的具体数值**：7.4 的权重是初始建议，实现者可调整，但必须保留四个维度分开计算。
6. **归档目录的领域分类**：`archive/<领域>/` 的领域清单由实现者提出初始建议，用户可自行增减。

## 十二、验收标准

### 12.1 v1 验收

| 编号 | 标准 |

### 12.2 Phase 2 验收

当近期文章引用一篇高相关的历史论文时，Skill 能将其识别为补充候选，而不是仅因发布时间较早就忽略。

### 12.3 Phase 3 验收

完成一次研究后再次运行，能利用之前的采集结果生成更具体的检索计划，并避免大量重复采集。

## 十三、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 模型凭记忆给出的来源大面积失效 | 首次体验差 | 明确标注待验证；提供粘贴 URL 路径；不自动采集 |
| 静态范围列表不准确 | 研究循环被错误阻断或跑偏 | 首次运行时生成建议范围供确认；用户可随时编辑 |
| 合规检查过于保守导致可用来源过少 | 工具显得没用 | 保守默认是有意的取舍；在报告中说明被阻断的原因与依据，让用户能判断 |
| 提示注入通过网页正文影响 Agent | 安全风险 | 10.5 的隔离与 Schema 校验 |
| 多轮摘要导致上下文膨胀 | 后期轮次质量下降 | 7.2 的三层结构 |
| 单人维护，依赖第三方站点结构 | 采集器失效 | 优先 API / RSS 而非网页解析；provider 可插拔 |
| 宿主 Agent 每轮交还时丢失上下文 | 轮次质量下降或状态错乱 | 5.6 的结构化交接包；交还点显式可校验；状态写入 `state/` 而非依赖上下文 |
| 用户在无 LLM 环境运行 | 得到看似成功的空壳数据 | 5.5 明确报错，不定义降级路径 |

### 14.2 由我提出、用户未逐条确认的决定

列出供检查：

1. **合规检查的保守默认**：robots.txt 不可达 → `ERROR`；条款无法判定 → `REVIEW_REQUIRED`
2. **归档目录用英文 slug**，中文只出现在内容里
3. **`max_rounds: 8`、`max_documents_per_research: 200`** 作为默认值
4. **`SKILL.md` 英文、用户文档中文、README 中英双版**
5. **范围列表为空时**由 LLM 生成建议范围，但需用户确认后才用于硬校验
6. **v1 不实现 `viewer.py`**，但保留文件占位与归档接口
7. **`REVIEW_REQUIRED` 的授权记录**写入 `source_policies.jsonl`，带范围与有效期
8. **行动时间窗口默认值**：`deepen`/`broaden` 近 180 天，`verify` 不限，`backtrack` 近 5 年
9. **`related` 范围行动做形式校验**（`scope_justification` 非空），不做语义校验
10. **未完成文档保留到下轮**，`attempt_count` 超 3 次转永久失败
11. **模型来源先做可达性检查**，与合规检查分成两步
12. **文档模型补充三个字段**：`date_confidence`、`round_discovered`、`attempt_count`
